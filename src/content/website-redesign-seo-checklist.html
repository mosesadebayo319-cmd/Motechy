A website redesign SEO checklist should protect the routes customers already use: useful pages, existing links and the enquiry that follows. Before approving the new design, record those routes, decide what changes and test each decision. A good-looking homepage is only one part of a successful launch.

Picture a Lagos print business replacing its website. A customer opens a flyer link saved in WhatsApp, but the new site sends them to a general homepage. Another scans a QR code on an old business card and reaches an error. The redesign may look better while making it harder to buy.

This guide uses that hypothetical business to explain what to check before, during and after launch. It is not a client case study or a promise of unchanged rankings. Download the editable website redesign launch checklist and use it to agree responsibilities with your developer.

Define what the redesign actually changes

Write a short scope statement: which pages, content, features and addresses will change? A new layout can keep the existing URLs. Moving /flyers.html to /services/flyer-printing changes a URL even when the domain stays the same.

Keep working addresses unless there is a clear reason to replace them. Ask what each proposed change helps a customer do. “The new template uses different names” is a problem to resolve with the developer, not a business benefit.

Treat domain registration, email accounts and hosting changes as separate decisions with their own agreed plan. A visual refresh does not automatically require them. Google’s site-move guidance distinguishes URL changes and recommends separating major changes where possible. Its Change of Address tool is not needed for path changes within the same domain.

Record the existing site before replacing it

Create an inventory from the current sitemap, content system and a crawl of the site. Add addresses found in brochures, adverts, social profiles and saved customer messages. Include PDFs and other downloads: the navigation menu alone may not reveal everything people still use.

For each address, record its purpose, title, main heading, important content, next action and whether it currently works. Mark pages that explain a valuable service or answer a recurring buying question. Save a recoverable copy of the site and its configuration before development replaces anything.

Where you have authorised Search Console access, export available page and query data with the date range and filters. The Performance report distinguishes clicks, impressions, click-through rate and average position. Those are search measures, not sales. Keep your enquiry records alongside them, and write “not available” when tracking is missing rather than inventing a baseline.

Decide the destination of each old address

Give every inventory row an explicit decision: keep, move, merge or retire. For a permanent move, Google recommends a server-side permanent redirect where possible; 301 and 308 identify permanent moves. See its redirect documentation. A renamed menu item does not create a redirect by itself.

Existing address Decision Acceptance check
/printing.html Move to /services/business-printing. The old link reaches the new page explaining the same service.
/flyers.html Move to /services/flyer-printing. Flyer specifications and the flyer enquiry route remain available.
/contact Keep the address. Current contact details and the correct service selection work.
/downloads/artwork-guide.pdf Keep the file address; review its contents. The actual PDF opens on a phone and contains current instructions.
/offers/old-promo Retire if expired, with no useful replacement. A genuine missing/gone response explains the situation and offers navigation.

Do not send every removed page to the homepage. Google’s site-move guidance warns that irrelevant redirects can be treated as soft 404 errors. A merged page is suitable only when it genuinely covers the old material. For a missing page, use a real 404; 410 explicitly means the resource is gone. MDN explains that distinction. An error message displayed with a successful-page response is not the same thing.

Have the developer record the initial response, final address and final response for every mapped URL. Check both the destination and its content. Remove loops and unnecessary intermediate redirects; a browser eventually reaching “something” is too weak an acceptance test.

Preserve the job the page does for a buyer

For the printer, the flyer page should still help someone understand available formats, artwork requirements, collection or delivery arrangements and how to request a quote. The owner must confirm those details. A large photograph and “quality printing solutions” do not replace practical buying information.

Review titles, headings, image descriptions and structured data against what each page actually says. Update internal links to the final addresses. If the business no longer offers something, correct the content instead of preserving an inaccurate promise for a keyword.

Check canonical links, which indicate a preferred address for duplicate or very similar content. They must not accidentally point to the preview site or contradict the intended public URL. Google’s canonical guidance explains these signals. A canonical link does not replace the redirect needed to send a visitor from an old address to a new one.

Check the preview and the mobile journey

Use a protected preview for unfinished work. Record how the preview is kept out of search and how production will be checked separately. A noindex rule can exclude accessible content from Google’s index, but it does not make that content private. Google must be able to crawl the page to read the rule; blocking it in robots.txt can prevent that. Follow the noindex documentation.

Open the proposed service page on a phone, follow its quote link and check the selected service. Try keyboard navigation, larger text and a slower connection. Does the page remain usable before a large image finishes loading? Can someone read the contact details without dismissing an obstructive overlay?

Test form validation and delivery behaviour in a controlled test environment with a test destination or simulated delivery. Cover accepted, rejected and failed requests; a success message must not appear after a failed delivery. Do not send dummy enquiries into a real sales inbox. W3C’s forms guidance covers labels, instructions and clear success/error feedback. These checks protect the business outcome after the visit.

Make a launch decision from evidence

Give one person responsibility for the release decision and another named contact for technical fixes. Agree when they are available, using Africa/Lagos time if the team works across time zones. Keep the old release and a documented recovery procedure available; restoring files alone may not restore changed content or configuration.

Before approving launch, require evidence that:

  • Important old URLs reach the agreed destinations, including brochure and QR-code links.
  • Public pages have the intended content, canonical addresses and crawl/index settings.
  • Images and downloads work, and the mobile enquiry journey selects the correct service.
  • Form success and failure paths passed controlled tests without contacting real customers.
  • The sitemap lists intended public canonical pages, not preview URLs or retired pages.
  • A release owner can pause or recover the launch if a critical journey fails.

Recheck the actual production site after deployment. Google’s sitemap guidance recommends fully qualified URLs and the canonical versions you want in search. Submit the updated sitemap through an authorised Search Console property; submission is not proof that every page has been indexed.

Watch for specific failures after launch

Record the release time and changes. Check key journeys immediately, then review errors and enquiry handling during the first working days. Use matched date ranges for later comparisons, accounting for weekdays, campaigns and seasonal demand. Treat this as an operating routine, not a guaranteed recovery timetable.

If a service page loses visits, first inspect its old and new addresses, redirect, content and index settings. If visits remain steady but enquiries stop, check the form and delivery path. If analytics alone goes quiet, confirm measurement still works before declaring that customers disappeared.

Search Console’s URL Inspection tool distinguishes the indexed version from a live test. A successful live test does not guarantee indexing. Google’s migration guidance also notes that rankings can fluctuate during site moves and recommends retaining redirects for as long as possible, generally at least a year. Give those redirects an owner beyond launch week.
